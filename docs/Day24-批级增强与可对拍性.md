# Day 24 · 批级数据增强：把 3.46 倍的开销压回去

> 昨天（Day 23）证明了两件事：增强确实压住了过拟合（最低 `val_loss` 降 35%、
> `gap` 从 +1.36pt 收到 +0.17pt），但它有一个硬代价 —— **每轮慢 3.46 倍**。
>
> 今天把代价拿回来。本来看起来是个"性能优化"的小任务，
> 实际做下去发现核心难点根本不在性能，在**可验证性**：
> 换一种执行方式之后，你还能不能说"结果没变"。

---

## 一、23.4 秒花在哪

Day 23 的实测：

| | 每轮耗时 |
|---|---|
| 无增强（baseline） | 9.48s |
| 有增强（±2 像素 + ±10°） | 32.84s |
| **差值 = 增强的净开销** | **+23.4s** |

先算一下它到底做了多少计算（实测：MNIST 训练集 60000 张切掉 6000 给验证，
剩 **54000** 张；`batch_size=128` → 每轮 **422** 批）：

```
每个 epoch 的图数        54000 张
每张图输出像素           28 × 28 = 784
每次 grid_sample 插值    每像素取 4 个邻居做双线性 → 4 次乘加
                         784 × 4 = 3136 次乘加 / 张
全 epoch 总乘加          54000 × 3136 ≈ 1.69 亿次
```

1.69 亿次乘加，在 CPU 上单线程跑单精度……其实也就是几十毫秒的量级。
可它花了 **23.4 秒**，差了两到三个数量级。

对照一下同一轮里的另一件事：CNN 的前向 + 反向，做的是
`conv1 + pool + conv2 + pool + fc1 + fc2`，总参数量 206,922，
每个样本要过两万多次乘加，54000 个样本 + 反向（约 3 倍前向）
≈ **1.2 万亿次乘加**，耗时 9.48s。

所以结论很清楚：

> **不是算得慢，是调得太碎。**

`AugmentedDataset.__getitem__` 每张图调一次 `warp`，形状是 `(1,1,28,28)`。
一个 epoch 调 **54000 次**。每次调用的固定成本（算子调度、
`affine_grid` 建网格、内存分配、Python ↔ C++ 的参数转换）
远大于它真正做的 3136 次乘加。

打个比方：不是搬砖慢，是每搬一块砖都要去前台登记一次。
砖本身没多重，手续重。

**优化方向因此很明确：把手续合并。** 一批 128 张图合并成一次调用，
固定成本从 128 次降到 1 次。

## 二、难关不在性能，在随机数

### 2.1 直觉做法，以及它埋的雷

把增强从 `Dataset.__getitem__` 挪到 `collate_fn`，代码只改十几行：

```python
def collate(batch):
    xs, ys = default_collate(batch)      # 128 个 (x,y) 拼成批
    xs = random_affine(xs, shift, angle, gen)   # 整批一次 warp
    return xs, ys
```

但它悄悄换掉了随机序列。看 Day 23 的抽样实现：

```python
tx  = rand(n)     # 消耗 n 个随机数
ty  = rand(n)     # 消耗 n 个
ang = rand(n)     # 消耗 n 个
```

**逐样本**时 `n=1`，被调用 128 次，第 i 次拿到 `(r[3i], r[3i+1], r[3i+2])`。

**整批**时 `n=128`，被调用 1 次，第 i 行拿到 `(r[i], r[128+i], r[256+i])`。

同一张图，两种挂法拿到的平移量**完全不同**。

### 2.2 为什么这是灾难，而不是"稍微有点不同"

因为一旦序列变了，优化前后就**不可比**。你会看到 loss 曲线对不上，
然后陷入一个无解的判断：

> 这是我把 collate 写错了，还是随机序列本来就变了？

**没有判据，就没有正确性。** 这比"慢 3.46 倍"严重得多 ——
慢只是浪费时间，不可验证是毁掉这一天的工作。

### 2.3 解法：让随机消耗与批大小无关

改成一次抽 `3n` 个，再 reshape 成 `(n, 3)`：

```python
raw = torch.rand((n, 3), generator=gen, dtype=dtype)   # 一次消耗 3n 个
p = (raw * 2.0 - 1.0) * torch.tensor([shift, shift, angle])
tx, ty, ang = p[:, 0], p[:, 1], p[:, 2]
```

行优先排列，于是：

```
样本 i 的参数 = (r[3i], r[3i+1], r[3i+2])
```

**与 n 无关，与分几次调用无关。** 这一个式子解决了三个问题：

| 问题 | 旧写法 | 新写法 |
|---|---|---|
| 批级 vs 逐样本抽样 | 不同 | **逐位相同** |
| 改 `batch_size` 会不会改增强强度 | 会（暗中） | **不会** |
| 能不能硬对拍 | 不能 | **能** |

### 2.4 一个必须实测的前提

上面第 1 行依赖一个假设：`rand(3n)` 一次抽出 == `3n` 次各抽 1 个。

这是**假设，不是知识**。不同随机数发生器行为不同，必须测。
实测（`_probe_rng.py`，测完即删）：

```
rand  dtype=float32  一次抽 vs 逐次抽  逐位相同=True
rand  dtype=float64  一次抽 vs 逐次抽  逐位相同=True
```

原因：PyTorch CPU 的生成器是 MT19937，它是**流式**的 ——
每次请求都从同一条流里接着取，不按请求长度重新播种。

### 2.5 一个副作用，必须交代

新写法**总是**抽 `3n` 个数，包括 `angle=0`（只有平移）的情况。
旧写法里，`angle=0` 时 `ang` 那一列**一个数都不抽**。

后果：

| 配置 | Day 23 序列 | Day 24 序列 |
|---|---|---|
| `aug0`（全 0） | 短路，不抽 | 短路，不抽 → **不变** |
| `aug1` / `aug2`（只有平移） | 抽 2n | 抽 3n → **变了** |
| `aug3` / `aug4`（两项都开） | 抽 3n，n=1 | 抽 3n，n=1 → **不变** |

所以 Day 23 的最优组（aug3）和 baseline 的序列**一位都没变**，
这一点下面第五节会用 105 个值逐位验证。aug1/aug2 变了 ——
它们不是最优剂量，结论（`val_loss` 降 20–34%、`gap` 收窄）是统计性的，
不依赖具体序列。

> **为什么接受这个副作用**：因为"随机消耗量只依赖样本数"这个性质，
> 比"省几个随机数"重要得多。它保证了**改剂量不会改变随机消耗节奏**，
> 也保证了批大小无关。取舍是拿两组中间的剂量换一条更硬的性质。

## 三、collate_fn 到底在哪

DataLoader 的一个 batch 是这样生产出来的：

```
Dataset.__getitem__  × batch_size    ← 逐张取：读数据、ToTensor、归一化
collate_fn           × 1             ← 把 128 个 (x,y) 拼成一个批张量
```

`collate_fn` 收到的是 `[(x0,y0), (x1,y1), ..., (x127,y127)]`，
默认实现 `default_collate` 就是把 list 里的张量沿新维度 stack 起来。

我们在这里插一脚：**先默认拼好，再对整批 warp**。

### 3.1 为什么不能"逐张 warp 再 stack"

```python
xs = torch.cat([random_affine(x.unsqueeze(0), ...) for x, y in batch])
```

这样写代码更简单，但一点没省 —— 还是 128 次调用。
省下来的全部来自"一次算子调用处理 128 张"。

### 3.2 为什么生成的随机流不会"用完"

`gen` 挂在闭包上，生命周期与 DataLoader 一样长。一个 epoch 结束，
它已经推进了 `3 × 54000` 个随机数，所以下一个 epoch 的变换自然是新的。
**不需要任何"每轮换一批参数"的代码。**

这一点和 Day 23 是同一个道理：随机性靠"生成器持续消耗"实现，
而不是"预先抽一批存下来"。后者会让每个 epoch 看到同样的增强图。

## 四、六关

`src/data/batch_aug.py --train`：

| 关 | 测什么 | 结果 |
|---|---|---|
| 1 | 批级抽样 == 逐样本抽样（8 次 n=1） | **0.00e+00** |
| 2 | 每样本参数与 `batch_size` 无关（bs=1/2/4/8） | **0.00e+00** |
| 3 | 给定同一组 theta，整批 warp == 逐样本 warp | **0.00e+00** |
| 4 | 端到端：`AugmentedDataset`+DataLoader vs collate+DataLoader | **0.00e+00**（4 个批全部） |
| 5 | 幅度全 0 时 == 原始管线 | **0.00e+00**，且**一个随机数都不消耗** |
| 6 | 速度 | 40.76ms → 0.87ms，**46.8 倍** |

### 4.1 关 3 为什么能逐位

`grid_sample` 在批维上是**逐样本独立计算**的：输出第 i 个样本
只依赖输入第 i 个样本和第 i 个 theta，样本之间没有任何归约
（contrast：卷积的 `∂L/∂W` 必须跨样本求和，Day 22 踩过）。

所以"批内 128 个一起算"和"一个一个算"在数学上是同一件事，
在实现上也是同一条数值路径 → 逐位相同。

**如果哪天换成需要跨样本归约的算子，这一关就会退化成 1e-7 量级，
那端到端就只能比统计量。** 逐位是可对拍性的最高级，不是默认就有的。

### 4.2 关 4 第一版失败：我自己埋的

第一版关 4 报错：

```
批 0   128   x 最大差 1.03e+00   y 相同 False
✗ 未通过：第 0 批标签顺序不同 —— shuffle 的随机流没对齐
```

原因：**一个 batch 的产出依赖两条随机流**，我只对齐了一条。

| 随机流 | 控制什么 | 我的第一版 |
|---|---|---|
| 增强的 `gen` | 每张图怎么变 | ✅ 两边都 `seed=0` |
| shuffle 的 `generator` | 样本顺序 | ❌ 一边 `seed=7`、一边 `seed=0` |

标签顺序都对不上，比出来的 `x` 差当然没有意义
（那个 `1.03e+00` 不是"增强写错了"，是"两张不同的图在比"）。

这条已经写进代码注释：**对拍前先把所有随机流列出来，一条一条对齐。**

## 五、最硬的验证：15 轮重跑，105 个值全对

六关是自测，还得在真实训练上看。做一次干净的复现实验：

```
同样 seed=0、同样 15 轮、同样两组剂量（aug0 / aug3）
Day 23：增强在 Dataset.__getitem__ 里，逐样本，54000 次调用
Day 24：增强在 collate_fn 里，整批，469 次调用
```

比 `history.json` 的全部确定性字段（`train_loss` / `train_acc` /
`val_loss` / `val_acc` / `gap` / `wnorm` / `lr`）：

| 组 | 15 轮 × 7 字段 | 不同的值 | test acc 旧 → 新 | best_val_acc 旧 → 新 |
|---|---|---|---|---|
| aug0 | 105 | **0** | 0.9900 → 0.9900 | 0.9898 → 0.9898 |
| aug3 | 105 | **0** | 0.9915 → 0.9915 | 0.9915 → 0.9915 |

**210 个确定性值，一个都没变。**

这句话的分量在于：它把"优化没改变结果"从我读代码得出的**推理**，

但数值一个字节都没动。

而且顺手验了 Day 22 的基线没被污染：`aug=0` 的前 10 轮与
Day 22 的 `cnn` 记录相比，7 个字段 × 10 轮同样逐位一致。

## 六、耗时账：三个数字，一个都不能少

| 口径 | 优化前 | 优化后 | 加速 |
|---|---|---|---|
| **单算子**（128 张 × 10 次微基准） | 40.76 ms | 0.87 ms | **46.8×** |
| **每轮增强净开销** | 23.4 s | 3.0 s | **7.9×** |
| **端到端每轮**（含前向反向） | 32.84 s | 13.55 s | **2.42×** |

三个数差得很远，差距本身是今天最值得记住的东西。

### 6.1 为什么单算子快 46.8 倍，净开销只快 7.9 倍

因为"增强的净开销"里，`warp` 只是其中一项。剩下的是：

```
每批要做的固定工作：
  · 128 次 Dataset.__getitem__（索引、ToTensor）
  · default_collate 的 stack（128 个张量拼成批）
  · Python 层遍历 batch 列表
  · 张量 H2D 拷贝
```

这些**优化前后都要做**，一分钱没省。按批算（每轮 422 批）：

```
Day 23：23.4s / 422 批 = 55.4 ms/批    ← 与微基准 40.76ms 同量级（微基准不含 collate 的 stack）
Day 24： 3.0s / 422 批 =  7.1 ms/批    ← 微基准 0.87ms + 非 warp 的固定成本
```

### 6.2 为什么端到端只快 2.42 倍

这是 **Amdahl 定律**的直接体现。设每轮总时间里的可优化部分占比为 `p`，
优化掉的部分被加速 `s` 倍，则总加速上界为 `1 / ((1-p) + p/s)`。

这里 `p = 23.4 / 32.84 = 71%`（增强占比），`s = 7.9`：

```
上界 = 1 / (0.29 + 0.71/7.9) = 1 / 0.379 = 2.64×
实测 = 32.84 / 13.55 = 2.42×
```

实测略低于上界，因为优化后的 collate 里 `default_collate` 的 stack
又被算进了计时（Day 23 是逐张 warp 后再 stack，路径不同）。

**这条定律的实用价值**：它告诉你优化的天花板在哪。
在增强占 71% 的时候，把增强优化到**无限快**，最多也只能到 3.4 倍
（`1/0.29`）。所以下一步再想快，就不能继续抠 `warp` 了 ——
必须动那 29%（数据加载、张量拷贝），或者上多进程 / 多线程。

### 6.3 一个诚实的说明

Day 23 记录过：同一配置两次跑，耗时波动 ±10%（`101.3→105.8s` 等），
而所有 loss/acc 一位没变。所以**耗时不能进 `history.json`**。

上面那些秒数也带这个不确定性。`32.84 → 13.55` 差 2.4 倍，
远大于 ±10% 的波动，结论是稳的；但 `9.48 → 10.57`（baseline 两天的差异）
就属于波动范围 —— **baseline 没变慢，也不能说它变快了。**

## 七、25 轮：aug3 到底在哪见顶

Day 23 只跑 15 轮，aug3 在 `patience=3` 下**跑满也没触发早停**，
说明它还在改善 —— 那 15 轮不足以判断"最优在哪一轮"。所以今天跑 25 轮。

### 7.1 结果：Day 23 的一个结论被推翻了

| 轮数 | baseline | aug3（±2 像素 + ±10°） | 差值 | t |
|---|---|---|---|---|
| 15 轮 | 0.9900 | 0.9915 | +0.15pt | 1.11（不显著） |
| **25 轮** | **0.9900** | **0.9936** | **+0.36pt** | **2.82（显著）** |

`SE_diff = sqrt(0.9936×0.0064/10000 + 0.9900×0.0100/10000) = 0.1275pt`
→ `t = 0.36 / 0.1275 = 2.82`

Day 23 我写的是"**精度提升不显著，如果只看这一列，结论是增强没什么用**"。
多跑 10 轮之后，这句话不成立了。

### 7.2 为什么会翻：baseline 早就到顶了，aug3 没有

关键在那两个"没变"和"变了"的数字：

| | baseline 15 轮 | baseline 25 轮 | aug3 15 轮 | aug3 25 轮 |
|---|---|---|---|---|
| test acc | 0.9900 | **0.9900** | 0.9915 | **0.9936** |
| best val acc | 0.9898 | **0.9898** | 0.9915 | **0.9933** |
| 最低 val_loss @ep | 0.0413 @7 | **0.0413 @7** | 0.0267 @13 | **0.0232 @20** |

**baseline 多跑的 10 轮完全白跑**：test acc 和 best val acc 一位没变，
最低 `val_loss` 还是在第 7 轮。它从 ep7 之后就没有任何新的最优点了。

看它的 `train_acc`：ep21 起就是 **1.0000**，`train_loss` 0.0003 → 0.0001。
54000 张训练图，一张不差全记住了。这就是 Day 22 说的"真过拟合"的终局。

而 aug3 的 `@ep` 从 13 推到 **20**，best val acc 从 0.9915 推到 0.9933。

所以增强的真实作用链是这样的：

```
增强抑制过拟合
    ↓
模型可以继续训练更久而不过拟合（窗口从 7 轮延到 20 轮）
    ↓
在更长的窗口里多榨出 0.36pt
```

**这条链是间接的，而且需要足够长的训练才显现。**
15 轮时 aug3 正好停在它自己的爬坡中途（`@ep=13` 已经很接近 15），
而 baseline 早就到顶 —— 差距被压缩成 0.15pt，看起来"不显著"。

### 7.3 一条方法论教训

Day 23 我说"增强不是提分工具，是防过拟合工具"。这话今天要修一下：

> 增强确实不直接提分，但它**通过延长可训练窗口间接提分**。
> 说"不显著"之前，要先确认两件事：
> ① 两者的最优点是否都已经落在训练轮数之内；
> ② 训练轮数是否足够长到让收敛发生。
>
> 15 轮时 aug3 的 `@ep` 是 13，`patience=3` 下跑满 15 轮都没触发早停 ——
> **这个信号当时就在，我看到了（Day 23 台账里写了），但没把它当成
> "结论不可靠"的证据，只当成"Day 24 再跑一次"的待办。**
> 早停没触发 = 曲线还在下降 = 这个轮数下的对比没有意义。

这和 Day 15 那个错误是同一类：**Day 15 是只测一个剂量点就下结论，
今天是只测一个训练长度就下结论。** 都是"用一个样本代表一条曲线"。

### 7.4 早停在这里露了一个小马脚

25 轮下，`loss` 判据 `patience=3` 会在**第 19 轮**停，而全局最低点在**第 20 轮**。
差了 1 轮，`best.pt` 存的是 ep17 的权重（val_acc 0.993167）而不是 ep20 的（0.993333）。

看精确的 `val_loss`：

```
ep13  0.026724          ← 旧的 best
ep16  0.023989          ← 新低，bad 清零
ep17  0.024007          ← 比 ep16 大 1.8e-5，bad=1
ep18  0.032911          ← bad=2
ep19  0.029064          ← bad=3 → 停
ep20  0.023163          ← 真正的全局最低，但已经停了
```

**1.8e-5 的差异，就消耗掉了一次 patience。** patience=3 实际上等于
"允许两次真正的反弹 + 一次微小抖动"，而不是"允许三次反弹"。

### 7.5 这个预测被实测证实了

上面那段是从 `history.json` 离线反推出来的，属于**预测**。
拿真实训练验证一下（`--config configs/cnn_aug.yaml`，25 轮，早停开 p=3）：

```
epoch 19/25  train loss=0.0263 acc=0.9914  |  val loss=0.0291 acc=0.9917
  [早停] 按 loss 判据已连续 3 轮没改善（patience=3）
  [早停] 实际跑了 19/25 轮，省下 6 轮 ≈ 92.1s
best val acc = 0.9932
test loss=0.0206  test acc=0.9933
```

| | 离线预测 | 实测 |
|---|---|---|
| 停在第几轮 | 19 | **19** |
| best val acc | 0.993167（ep17） | **0.9932** |

**完全对上。** 这就是"一次训练反推 10 种早停策略"这个方法的可信度证明 ——
早停只读验证曲线，所以它是曲线上的一个确定性函数，离线算和真跑必然一致。

代价也很清楚：

| | test acc |
|---|---|
| 跑满 25 轮（早停关） | **0.9936** |
| 早停 p=3（停 19 轮） | 0.9933 |
| 差 | 0.03pt = **3 条测试样本** |

**早停在这里省了 92 秒，付了 3 条样本。** 这个交换是否值得，
取决于你在不在乎 0.03pt —— 但至少现在两边都是实测数，不是感觉。

## 八、一条元教训：关卡本身会过期

改完实现之后，Day 23 的**关 7 会开始误报**。

它原来这么写：

```python
is_aug = [isinstance(d.dataset, AugmentedDataset) for d in (tr, va, te)]
assert is_aug == [True, False, False]
```

判据是"`train_set` 是不是被 `AugmentedDataset` 包了"。今天增强挪到了
`collate_fn`，`Dataset` 不再被包装 → `isinstance` 恒为 `False` →
这一关会一直报"增强装错了地方"，**而增强好得很**。

这跟 Day 23 那个 `__main__` 双份模块的坑长得很像（报错说增强没生效，
其实是断言用错了），但根子不同：那次是我写错了类，这次是**判据过期**。

修法是把判据换成与实现无关的东西 —— 给 `collate` 挂一个属性：

```python
collate.__augment__ = {"max_shift": ..., "max_angle": ...}
```

然后 `has_augment(loader)` 看这个属性。判据从"某一种挂载方式"
变成"有没有挂载"，就跟实现解耦了。

> **规律**：断言写"实现细节"最省事，但一改实现就失效；
> 断言写"行为特征"要动点脑筋，但能活得更久。
> Day 23 的关 2（整数平移逐位对拍）之所以到现在还能用，
> 就是因为它断言的是"输出应该长什么样"，不是"代码怎么写的"。

### 9.2 我自己犯的错（三个）

1. **关 4 只对齐了增强的 seed，忘了 shuffle 的 seed** ——
   一个 batch 的产出依赖两条随机流，漏一条就没法比。被关 4 自己抓出来。
2. **又一次用 `p.split('/')[-2]` 取目录名** ——
   Windows 上是反斜杠，直接 `IndexError`。这是 Day 23 第 5 条错误的原样重犯，
   正确写法 `Path(p).parent.name`。**知道不等于会用，这类错要靠模板固化。**
3. **讲义第一版里的"每轮 63303 张 / 469 批"是我编的** ——
   实测是 **54000 张 / 422 批**（MNIST 60000 切 6000 给验证，再除 batch 128）。
   这些数字一路牵连了 1.98 亿次乘加、每批 49.9ms 等好几处推导。
   危险的地方在于**它看起来完全合理**：63303 既不像 60000 也不像 65536，
   编得像个真实测出来的数。所以下面的推导全对，只有输入是假的。

   > 规矩：**讲义里的每个数字要么来自实测输出，要么标"估算"。
   > 不许写一个"大概是这么多"的数。** 这次是自己复核时发现的，
   > 但如果没复核，这条错误会一直躺在文档里，将来被当成前提引用。

### 9.4 三条跨天结论

1. **"换实现"能不能硬对拍，取决于随机数在什么时候被抽。**
   Day 22 换算法（im2col）→ 逐位；Day 23 换数值路径（grid_sample）→ 1e-15；
   Day 24 换执行时机 → 先把随机消耗改成批大小无关，于是**又逐位了**。
   执行方式本身不改变数值，破坏对拍的是随机流。
2. **性能优化必须先保住可验证性，再谈速度。**
   如果先改 collate 再"顺手"改抽样，你会同时改了两个东西，
   曲线对不上时无法归因。顺序反过来（先改抽样、用关 1/2/3 确认等价，
   再改执行位置、用关 4 确认端到端等价）—— 每一步只改一件事。
3. **Amdahl 定律决定了优化的天花板，要先算再动手。**
   增强占 71% 时把增强优化到无限快，端到端最多 3.4 倍。
   不知道这个数的时候，很容易在已经榨干的地方继续抠。
