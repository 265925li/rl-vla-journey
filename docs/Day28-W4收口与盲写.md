## 一、W4 做了什么（Day 22–27）

六个学习日，五个实测结论，其中**三个和预期相反**。

| Day | 做了什么 | 最重要的数字 |
|---|---|---|
| 22 | CNN + im2col 手写卷积 | test **0.9889**（MLP 天花板 98.1） |
| 23 | 数据增强（平移 2px + 旋转 10°） | 15 轮 0.9915，t=1.11 **不显著** |
| 24 | 批级增强 + 25 轮 + 早停 | **0.9936，t=2.82 显著**；每轮 32.84s → 13.55s |
| 25 | 手写 BatchNorm2d | 精度测不出（t=1.57）；**ep1 val_loss 快 41%**；gap 收窄 78% |

### 1.1 三条和预期相反的结论

1. **Day 24 的"剩下的 4.07s 是数据加载"是错的。** 实测数据侧是 9 秒，
   而且 8.29s 花在 `__getitem__` 的 PIL 往返上 —— 增强只占 0.45s。
   Day 24 花一整天优化的东西只占 3%。
   **倒推的拆解不是测量。**

2. **Day 25 的 BN 在 MNIST 上测不出精度提升。** 它真正的作用是
   收敛快 41%、过拟合收窄 78%、以及一个**只在小尺度下才失效**的
   尺度不变性（`σ² ≈ ε` 时偏差 13.7%）。

3. **Day 26 的 amp 在这台机器上更慢。** sm_75 的消费卡（TU116）没有
   Tensor Core，同一个 batch 大小下慢 1.56 倍，batch 越大差距越大（4.15 倍）。
   省显存是真的，提速是假的。

### 1.2 一张表看清"每个手段改了什么"

| 手段 | 提高精度上限 | 加快收敛 | 抑制过拟合 | 提速度 |
|---|---|---|---|---|
| 数据增强（Day 23/24） | 否 | 否（更慢） | **是**（窗口 7→20 轮） | 否 |
| BatchNorm（Day 25） | 否 | **是**（4→2 轮） | **是**（gap +0.27→+0.06） | 否 |
| amp（Day 26） | 否 | 否 | 否 | **否（更慢）**，省显存 |
| 数据后端（Day 27） | 否 | — | — | **是（3.74x）**，数值不变 |

**四个手段里只有一个真的加速了，它恰好是最"不高级"的那个**
（把 `Image.fromarray` 换掉）。另外三个都是"改变优化过程"而不是"加速"。

> 这条是 W4 最该带走的东西：**"高级技术"和"有效"是两件事。**
> 而它们的区别只能靠测出来 —— 三个反直觉结论，两个是"量一遍"就发现的。

### 1.3 两个跨阶段的方法论升级

**① 实现噪声的基准线 = 2.0 SE（Day 25 立）**

换一个算法完全相同、单步差 `1e-15` 的实现，25 轮后 test acc 能差 **0.24pt**。
所以**要下"某手段有效"的结论，效应量得明显大于 0.3pt**，
而且至少要 3 个 seed 比均值。0.2pt 以内的单 seed 差异说明不了任何事。

回头审 W4 的全部结论：

| 结论 | 差值 | t | 超过 2 SE 吗 |
|---|---|---|---|
| Day 23 增强（15 轮） | 0.15pt | 1.11 | 否 → 当时判"不显著"是对的 |
| Day 24 增强（25 轮） | 0.36pt | 2.82 | **是 → 站得住** |
| Day 25 BN（lr.05） | 0.19pt | 1.57 | 否 |
| Day 25 BN（lr.10） | 0.14pt | 1.13 | 否 |

**② 进度条会骗人，通过/不通过不会（Day 22–27 累计）**

| Day | 关卡数 | 一次通过 | 修了几次 |
|---|---|---|---|
| 22 手写卷积 | 7 | 4 | 3 |
| 23 增强 | 7 | 5 | 2 |
| 24 批级增强 | 6 | 4 | 2 |
| 25 BatchNorm | 7 | **7** | 但真 bug 活过了七关 |
| 26 amp | 6 | 5 | 1（关 5 的假设错） |
| 27 数据后端 | 6 | 5 | 1（关 6 的断言错） |

## 二、W4 的四个决定

### 2.1 为什么 CNN 之后不继续调结构

Day 22 的 CNN 到 0.9889，之后三次改动（增强 / BN / amp）**没有一次提高了上限**。
MNIST 这个任务已经饱和 —— `best val_acc` 在四组配置里全是 0.9932~0.9933。

继续在 MNIST 上调结构，投入产出比会越来越差。
**任务饱和本身就说明该换任务了**，这就是 W5 转 RL 的理由。

### 2.2 为什么 amp 的默认值是 `none`

实测更慢、更耗精度，只有一个真实收益（省显存）。
**默认值跟着实测走，不跟着流行说法走。**

等模型大到 fp32 装不下，或者换到有 Tensor Core 的卡，再改。
这和 `data_backend` 默认设成 `u8` 是同一条原则的两个方向：
u8 因为没有取舍所以设成默认；amp 因为有取舍所以不设。

### 2.3 为什么 `data_backend` 默认用 `u8` 而不是 `f32`

`u8` 与 `pil` 逐位相同、零额外内存、快 2.26 倍 —— **没有取舍的改动**。
`f32` 再用 179MB 换 1.6 倍 —— **有取舍**，所以留成可选项。

**判据：有取舍的优化设成可选，无取舍的优化设成默认。**

### 2.4 为什么不再碰 `num_workers`

三个独立原因，每一个都不是调参能解决的：

1. 挂增强的 collate 原来是闭包 → 不可 pickle → 起不来（已修成类）
2. generator 被原样复制给每个 worker → 增强参数重复 → **改变数值**
3. Windows spawn 每 worker 5.1 秒 → **慢 8 倍**，`persistent_workers` 也只缓到 3.5 倍慢

而且做完 2.3 那个提速之后，它从"值得考虑"变成"绝对不要"。

> **优化完瓶颈之后，原来的第二瓶颈会变成新瓶颈，而它的方案未必还成立。
> Amdahl 定律要用两次。**

### 3.1 规则（必须严格遵守，否则验不出东西）

| 写完必须跑 `--check` | 自己觉得对不算 |
| 卡住时**先记录卡在哪**，再去看参考 | 卡点本身是最有价值的信息 |

**盲写期间不要打开这些：**

```

```

### 3.2 只有一件事要做

打开 `scripts/blind_train_step.py`，只有这一个函数是空的：

```python
def train_step(model, x, y, loss_fn, optimizer):
    """跑一步训练，返回这一步的 loss（标量张量）。"""
```

**契约（五条，缺一条过不了关）：**

1. 模型必须处于**训练态**（函数内部保证，不依赖调用方）
2. 必须清掉上一步留下的梯度（不依赖调用方先 `zero_grad`）
3. 前向 → 算 loss → 反向 → 更新参数，顺序固定
4. 返回值必须是**标量张量**，而且**仍带计算图**
   （不是 `.item()` 的 float，不是形状 `(1,)`）
5. 传入的 `x`/`y` 已在正确设备上，函数内**不需要** `.to(device)`

### 3.3 怎么验

```
& "E:\anaconda\envs\pytorch\python.exe" scripts\blind_train_step.py --check
```

| 关 | 测什么 | 判据 |
|---|---|---|
| 1 | 返回值 | 是 0 维 Tensor，且 `grad_fn` 不为 None |
| 2 | 参数 | 全部参数张量都变了 |
| 3 | 梯度 | 连续两次调用，梯度比值 < 1.5（不累加） |
| 4 | **行为等价** | 100 步 loss 序列与 `train_one_epoch` 逐位相同（< 1e-6） |

第四关是最硬的，也是最"宽容"的：它**不比代码比行为** ——
用 `zero_grad(set_to_none=True)`、用 `with torch.no_grad():` 之外的任何等价写法都能过。

> 关卡本身已经实测过：
> - 参考实现 → **4/4 通过**，100 步 loss 最大差 `0.00e+00`
> - 故意漏掉 `zero_grad` 的错误实现 → **2/4**，
>   梯度比值 `2.049`、loss 最大差 `7.28e+01`
>
> 所以"过了"是真的过了，"没过"也真的没过。


## 四、如果卡住了，不要有挫败感

**那才是真实的信息。**

P0 到 Day 27 的所有代码都是"我写、你读"。这条路能走到 CNN + BN + amp
这一点本身就说明理解没问题 —— 但"能读懂"和"能写出"之间隔着一段
只有亲手写才能跨过去的距离。

几个具体建议：

1. **先只写第 2 步。** 契约里说"必须清掉上一步的梯度"，那对应哪个方法？
   想不出来就先去看 `torch.optim.SGD` 有哪些方法 —— **看 API 不算看答案。**
2. **写不出来的那一步，写一句中文。** 比如"这里应该做一件让梯度归零的事"。
   然后再想它叫什么。**先有动作，再有 API 名。**
3. **别一次把五行写完。** 写两行就跑一次关 1。关 1 只查返回值，
   能先验证"前向 + 算 loss"这一段是对的。

> 参考实现只有 6 行（含 `return`）。6 行不该花超过 3 分钟 ——
> 如果超了，说明这 6 行背后的东西还没变成"你的"，而是"你读过的"。
> 这两者的区别，就是今天要测的东西。

## 附录 A · 参考实现

> **先填完卡点记录再看这一段。**
> 提前看的话，今天这一天就白过了 —— 你会得到"我会了"的错觉，
> 而 P2 的教学方式会按那个错觉去设计。

它在 `src/engine/loops.py` 的 `train_one_epoch` 里，也在这里：

```python
def train_step(model, x, y, loss_fn, optimizer):
    model.train()                 # 契约 1
    optimizer.zero_grad()         # 契约 2
    logits = model(x)             # 契约 3 之前向
    loss = loss_fn(logits, y)     # 契约 3 之算 loss
    loss.backward()               # 契约 3 之反向
    optimizer.step()              # 契约 3 之更新
    return loss                   # 契约 4（loss 仍带计算图）
```

**六个动作，对应契约五条。** 其中契约 5（不搬设备）在代码里表现为"什么都不写"。

### A.1 几个容易写错的地方

| 写法 | 问题 |
|---|---|
| `return loss.item()` | 违反契约 4：float 没有 `grad_fn` |
| `model.zero_grad()` | 能用，但它只清模型参数的梯度，**清不到优化器里动量以外的状态**；`optimizer.zero_grad()` 才是配套用法 |
| 把 `optimizer.step()` 写在 `loss.backward()` 之前 | 不报错，用上一步的梯度更新 → 相当于"每一步都慢一拍" |
| 漏了 `model.train()` | MLP 上数值无差别（没有 dropout/BN），但**契约要求**，而且加 BN 之后会静默错 |
| `loss.backward(); optimizer.zero_grad()` | 把刚算的梯度擦掉了 → 参数永远不动，但**不报错** |

最后那一行值得单独说：它会让 `gate2_params_moved` 报"0/20 个参数变了"。
**这就是关卡的价值 —— 一个"不报错但没有效果"的错误，只能靠断言抓。**

### A.2 一个可以讨论的点

`zero_grad()` 默认是"把梯度置 0"，`zero_grad(set_to_none=True)` 是"把 `.grad` 设为 None"。

后者**更快**（省一次写内存），而且能区分"梯度是 0"和"梯度没算过"。
实测上两者数值完全一样，四关都能过。

那为什么现有管线用的是默认值？

> 因为 Day 11 写这段代码时还不知道 `set_to_none`。
> **这不是"最优写法"，是"当时的写法"。**
>
> 这条值得留给以后的自己：**当你能看出旧代码的改进空间时，
> 说明这一层真的掌握了。** 今天如果看出来了，把它记在卡点记录的最后一栏。
