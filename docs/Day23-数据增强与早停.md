## 一、为什么只剩「加约束」这一条路

过拟合的本质是「模型容量 > 数据能提供的约束」。
治它只有两条路，Day 15 已经替我们排除掉了一条。

### 路子 A：降容量（正则化）—— 已经被实测排除了

Day 15 扫过 `weight_decay` 的剂量：

| wd | test acc | 相对 0 |
|---|---|---|
| 0 | 0.9800 | — |
| 5e-5 | 0.9804 | +0.04pt |
| **1e-4** | **0.9812** | +0.12pt |
| 5e-4 | 0.9782 | −0.18pt |

倒 U 型，峰值只有 +0.12pt，而验证集 10000 条的标准误是 0.14pt
——**这个提升不显著**。四组 dropout / wd 对照全部让精度下降。

结论：在 MNIST + 这个规模上，正则化不是有效手段。

### 路子 B：加约束（数据增强）—— 今天要走的

|  | 正则化 | 数据增强 |
|---|---|---|
| 做法 | 限制模型能表达什么 | 要求模型在更多输入上正确 |
| 比喻 | 把假设空间缩小 | 把考场扩大 |
| 风险 | 可能把**有用**的函数也压掉 | 可能造出**错标签**（把 6 转成 9） |
| MNIST 实测 | 精度下降 | 待测 |

差别就在"风险"那一行：
`weight_decay` 是无差别地压所有参数，它压不掉"过度拟合噪声"和
"学会真实笔画"之间的区别，所以 MNIST 上精度反而降。
增强只是**增加必须答对的题**，不限制模型能表达什么 ——
它没有"压过头把有用的也压掉"这个副作用，只有"造错题"的风险。

**所以增强的剂量不能随便给**。转 30°，6 就变成 9 了，标签成了噪声。
这就是为什么今天必须扫剂量，而不是拍一个数。

## 二、核心只有两个公式

### 2.1 仿射矩阵 theta

一次「平移 + 旋转」在数学上就是一次仿射变换，用 2×3 矩阵表示：

```
theta = [[ cos,  -sin,  tx ],
         [ sin,   cos,  ty ]]
```

它回答的是一个问题：**输出图的第 (r, c) 个格子，去输入图的哪里取值？**

- 第 0 行算 x（列方向），第 1 行算 y（行方向）
- 前两列是旋转 + 缩放，第 3 列是平移
- 注意这是「输出 → 输入」的映射，所以想让图**向右**移动 t 像素，
  平移项要写 **−t**。写成 +t 的话图会朝反方向跑。关 2 会当场抓住。

### 2.2 归一化坐标

`affine_grid` 不认像素，只认 [−1, 1] 的归一化坐标：

```
x_norm = (2 * col + 1) / W - 1
```

为什么要 `+1` 再 `-1`：因为 `align_corners=False` 时坐标指向**像素中心**。
第 col 列的中心在 `(col + 0.5) / W` 处，不是左上角的 `col / W`。

这个半像素如果搞错，整数平移就会整体偏半个像素 —— 不会报错，
只会让图模糊一点点，然后你会以为是插值算法的问题。

### 2.3 一个像素 = 2/W 个归一化单位

归一化坐标跨度是 2，对应 W 个像素，所以：

```
1 像素 = 2 / W 个归一化单位
```

28×28 的图上，移动 1 个像素 = 移动 0.0714 个归一化单位。
`make_theta()` 里那个 `/ half` 就是做这件事的。

## 三、三个坑（都在自测里验过）

### 坑 1 整批一个参数 ≠ 每个样本一个参数

theta 的形状是 `(N, 2, 3)`，第 0 维就是 batch。
如果只抽**一个**标量再复制 N 份，那么整批 128 张图会被同一个变换处理
—— 等价于"把整个 batch 当成一张图转了一下"，增强效果接近于零。

**这种错法有两条路径，一条被拦住，一条不会：**

| 写法 | 形状 | 结果 |
|---|---|---|
| `theta` 造 `(1,2,3)` 传给 batch=6 | 不匹配 | **RuntimeError 拦住** |
| 抽一个值 `full((6,))` 复制 6 份 | 合法 | **静默，每样本相同** |

第二种才是真坑：形状完全合法，跑得通，只是"增强没效果"。
实测六张图亮点列号 `[14, 14, 14, 14, 14, 14]` —— 一模一样。

### 坑 2 增强只能用在训练集

给验证集也加随机变换，`val_loss` 就变成"一个随机变量的实现"：
同一个模型的两次评估能差出好几个百分点。

后果不是精度掉，而是**早停失效** —— 早停靠 val_loss 判断"有没有变好"，
当测量本身带随机噪声时，它会在随机抖动上触发，
你会得到一个完全无法复现的停止点。

所以这一条不能靠自觉，得靠结构：`build_loaders()` 里只包装 `train_set`，
`val_set` / `test_set` 原样返回。关 7 用 `isinstance` 断言这一条。

### 坑 3 随机数生成器必须是持久的

如果在 `AugmentedDataset.__init__` 里把 60000 组参数一次性抽好存下来，
那么**每个 epoch 看到的增强图完全一样**。训练两轮就记住了，
增强退化成"把数据集换成了一套固定副本"，等于没做。

正确做法：生成器挂在 `self` 上，在 `__getitem__` 里现抽。
这样第 1 个 epoch 的第 0 张图和第 2 个 epoch 的第 0 张图拿到不同的变换。

**这个错特别值得记，因为它不报错、不掉精度得很明显**，
只是"增强好像没什么用" —— 属于最难查的那一类。

### 4.1 关 1/关 2 为什么不是「逐位相同」

Day 22 的 im2col 与 `F.conv2d` 能做到 **`0.00e+00` 逐位相同**，
因为两者走的是同一条 GEMM 路径。

**这里做不到，而且不该要求做到。** `grid_sample` 是另一条路径：
它自己算归一化坐标，再插值。而 `(2i+1)/28` 里的 1/28 不是二进制有限小数，
fp32 存不下，采样点就偏了不到亿分之一，双线性插值的权重
从精确的 `(1, 0, 0, 0)` 变成 `(0.999998, 2e-7, ...)`，于是差 1e-6。

**怎么证明"是精度问题而不是逻辑错"？把精度提上去再测一次。**

```
fp32  1.91e-06
fp64  3.55e-15      ← 小了 5 亿倍
```

如果 fp64 下还是差这么多，那就是坐标顺序/符号这类逻辑错 —— 换精度救不了。
这个「用提升精度来给误差归因」的动作，比盯着 1.91e-06 猜半天有用得多。

而且有一个很反直觉的实测现象：

| (tx, ty) | fp32 最大差 |
|---|---|
| (0, 0) 恒等 | **1.91e-06** ← 最大 |
| (1, 0) | 9.54e-07 |
| (−1, 2) | 0.00e+00 |
| (3, 1) | 0.00e+00 |

**恒等变换的误差反而最大，平移 3 像素却是零误差。**
说明误差大小和"移动了多少"完全无关，只取决于
「归一化坐标能不能被二进制精确表示」。这也再次证明它是舍入，不是逻辑。

### 4.2 关 3 的两种错法

| 写法 | PyTorch 反应 |
|---|---|
| `theta` 造 `(1,2,3)`，x 是 6 张 | `RuntimeError: Expected size ... [6,3] but got [1,3]` |
| 抽一个值复制成 `(6,)` | **静默通过**，六张图一模一样 |

同样是"参数传错了"，一种被框架拦住，一种只能靠自己。
**这就是为什么要给每个坑配一个断言**。

### 4.3 关 6 为什么必须用「亮点位置」而不是"看起来转了"

旋转这件事有三处独立的符号自由度：

1. 旋转矩阵里 `-sin` 放在哪个位置
2. 图像坐标系 y 是向下的（数学习惯是向上）
3. `affine_grid` 的网格最后一维是 `(x, y)` 顺序，不是 `(row, col)`

三处里任意一处写反，图**看起来照样在转**，只是方向反了。
肉眼完全无法判断 —— 除非你放一个已知位置的亮点，断言它转到哪里。

实测：右侧 `(row=14, col=20)` 的亮点，转 +90° 后到 `(row=7, col=13)`。
**右 → 上，视觉上是逆时针**。同时中心亮点转 37° 后仍在 `(14, 13)`。

### 4.4 关 7 的一个意外

本来以为「旋转四角填 0 会让均值下降」，实测**均值几乎不动**（−0.0%）：

| | 均值 | 标准差 | 亮像素占比 |
|---|---|---|---|
| 原始 | 0.1305 | 0.3082 | 0.1320 |
| 增强后 | 0.1305 | 0.2894 | 0.1306 |
| 相对变化 | −0.0% | **−6.1%** | −1.1% |

原因：MNIST 背景本来就是 0，填 0 填的是背景色，均值当然不动。
而标准差**降了 6.1%** —— 因为双线性插值把笔画锐利的边缘磨平了一点，
极值被拉低。这个方向和我预判的相反。

**预判错了不丢人，写了断言没抓住才丢人。**
所以关 7 的断言是「变化幅度在个位数百分比内」，而不是
「均值必须下降」—— 后者是我基于错误直觉写的，会把对的实现判错。

### 5.2 三条读数，重要性递增

**读数一：精度提升不显著。**

aug3 的 0.9915 vs baseline 的 0.9900，差 **0.15pt**。
合并标准误：

```
SE_diff = sqrt(0.9915×0.0085/10000 + 0.9900×0.0100/10000) = 0.135pt
t = 0.15 / 0.135 = 1.11
```

**1.1 个标准误，不显著。** 而且四组增强之间
（0.9904 / 0.9909 / 0.9915 / 0.9915）差得也很小，都在噪声内。

如果只看这一列，结论是"增强没什么用"。**这就是只测一个指标会得到的错误结论。**

**读数二：`val_loss` 的绝对水平被压下去三分之一。**

| | 最低 val_loss | 相对 baseline |
|---|---|---|
| baseline | 0.0413 | — |
| 轻 ±1 | 0.0329 | −20% |
| 中 ±2 | 0.0272 | −34% |
| **中上 ±2+10°** | **0.0267** | **−35%** |
| 重 ±3+15° | 0.0288 | −30% |

四组增强全部下降 20–35%，方向一致，幅度大。
`val_loss` 是连续量、分辨率远高于 acc（Day 15 算过：6000 条验证集里
正确 1 条只挪 0.0167%），**这个证据比 acc 那一列强得多**。

**读数三（最重要）：过拟合被单调抑制，`gap` 随剂量单调下降。**

| | 末轮 train_acc | 末轮 val_acc | 末 gap |
|---|---|---|---|
| baseline | **0.9987** | 0.9852 | **+1.36pt** |
| 轻 ±1 | 0.9950 | 0.9883 | +0.66pt |
| 中 ±2 | 0.9915 | 0.9867 | +0.49pt |
| 中上 ±2+10° | 0.9907 | 0.9890 | +0.17pt |
| 重 ±3+15° | 0.9881 | 0.9887 | **−0.05pt** |

**两列都是单调的**：剂量越大，`train_acc` 越低、`gap` 越小。
这正是数据增强该有的样子 —— 它让模型"记不住"训练集，
所以 train_acc 必然下降；而 val_acc 基本不动，于是 gap 收窄。

**这就是增强的全部价值：它不是提分工具，是防过拟合工具。**

### 5.3 一个必须看懂的信号：负 gap 不是好事

最后一组（±3+15°）的 `gap` 是 **−0.05pt** —— train_acc 比 val_acc 还低。

初看像"完美泛化"，其实是**欠拟合**：
训练集被增强得太狠，模型连训练集都拟合不了（train_acc 只有 0.9881）。

而且它的 `@ep` 掉回了 8 —— 前面几组把最优点推到 13、14 轮，
它却在第 8 轮就见底了。再往后 7 轮都是白跑。

**判断增强是不是过头了，看两个数**：
- `train_acc` 掉到 val_acc 附近甚至以下 → 过头了
- `@ep` 明显提前 → 过头了

### 5.4 结论

**最优剂量是 ±2 像素 + ±10°**（aug3）：
精度并列最高、`val_loss` 最低、`gap` 收窄到 +0.17pt 且没进入欠拟合区。

为什么要扫这一圈，Day 15 的教训说得很直白：
如果只测 ±2 那一组，你会看到 0.9904 —— **比 baseline 的 0.9900 只高 0.04pt**，
于是得出"增强没用"。只有把 ±2 配上旋转、把 ±3+15° 也跑出来，
才会看见"精度在 aug3 见顶、再往上就进入欠拟合"这条完整的曲线。

## 六、早停：一次训练反推 10 种策略

早停是**只看验证曲线**做的决策。给定一条已记录的 `val_loss` / `val_acc` 序列，
"patience=p 时会在第几轮停"是可以离线算出来的确定函数。
所以不用为每种策略各训一遍 —— 那样还引入了随机性，10 种策略根本不可比。

### 6.1 结果

| 剂量 | 判据 | p=1 | p=2 | p=3 | p=4 | p=5 |
|---|---|---|---|---|---|---|
| baseline | loss | 8 | 9 | 10 | 11 | 12 |
| baseline | acc | **3** | 8 | 9 | 10 | 15* |
| 轻 ±1 | loss | 7 | 8 | 9 | 10 | 15* |
| 轻 ±1 | acc | 6 | 7 | 8 | 9 | 10 |
| 中 ±2 | loss | 7 | 8 | 15* | 15* | 15* |
| 中 ±2 | acc | **3** | 8 | 9 | 15 | 15* |
| 中上 ±2+10° | loss | **3** | 8 | 15* | 15* | 15* |
| 中上 ±2+10° | acc | **3** | 11 | 12 | 15* | 15* |
| 重 ±3+15° | loss | 3 | 10 | 11 | 12 | 13 |
| 重 ±3+15° | acc | 3 | 10 | 11 | 12 | 13 |

（数字 = 会在第几轮停；`*` = 没触发，跑满 15 轮）

### 6.2 三条结论

**① `patience=1` 在两个判据下都会被噪声带走。**

baseline 的 loss 判据 p=1 停在第 8 轮，看起来正常（`@ep=7`，7+1=8）。
但 acc 判据 p=1 **停在第 3 轮** —— 而它的最优 val_acc 在**第 13 轮**。

差 10 轮。这就是 Day 15 说过的"acc 是离散量，被量化噪声带偏"：
6000 条验证集里正确 1 条 = 0.0167%，第 3、4 轮 acc 恰好没涨，
p=1 立刻判定"不改善了"。

更麻烦的是 aug3：它的 loss 判据 p=1 也停在第 3 轮。
也就是说**连 loss 判据在 p=1 时都不可靠** —— 单轮的 loss 抖动足以骗过它。

**② `patience >= 3` 才稳定。**

baseline 在 p=3/4/5 分别停在 10/11/12 轮，正好是 `@ep + p = 7 + p`。
aug3 在 p>=3 时全部跑满 15 轮。

**③ 增强之后 15 轮不够长。**

aug3 在 p=3 时**跑满 15 轮都没触发早停**，说明到第 15 轮还在改善。
这不是 bug，是增强的必然结果：每轮看到的信息量变少了（同一张图每次都不一样），
自然需要更多轮才能收敛。

所以 `configs/cnn_aug.yaml` 里的 `epochs: 15` 其实偏短。
**Day 24 的第一件事应该是把 aug3 跑到 25 轮**，看它到底在哪里见顶。

### 6.3 一个容易忽略的点

Trainer 存的是 **`best_val_acc` 那一轮**的权重，不是最后一轮。
所以在"训完 load best.pt 测 test"的设定下：

> **早停不改变最终模型，它只省时间。**

它的真实风险是**停得太早，把后面可能出现的更高点掐掉了** ——
比如 acc 判据 p=1 在第 3 轮停下，就永远拿不到第 13 轮那个 0.9898。

这也解释了为什么上表要同时给出 `@ep`：
**停的轮数应该 ≈ `@ep + patience`**。差太多就说明这个判据在该曲线上不稳。

## 七、两个代价，一个旧 bug

### 7.1 增强让每轮慢了 3.46 倍

| | 单轮耗时 |
|---|---|
| baseline（无增强） | 9.48s |
| ±2 + ±10° | **32.84s** |

原因很清楚：`AugmentedDataset.__getitem__` 对**单张图**做一次
`random_affine`，一个 batch 就是 128 次独立的 `make_theta + affine_grid + grid_sample`。
这 128 次小算子调用全在 **CPU 上、主进程里、串行执行**
（`num_workers=0`），而 GPU 训练本身只要几秒 —— 于是整条流水线被数据增强主导。

三个优化方向，从易到难：

1. **`num_workers=4`** —— 最省事，但 Windows 上要多写 `if __name__ == "__main__"`
   保护，而且 `self.gen` 会被每个 worker 复制一份，
   导致所有 worker 生成**完全相同**的随机序列（坑 3 的变体），必须改成
   用 worker 自己的 `torch.initial_seed()` 初始化。
2. **在 `collate_fn` 里整批增强** —— 一次 `warp` 处理 128 张，
   GPU 上几乎是免费。这个改动最干净，但要把增强从 Dataset 挪到 collate。
3. **缓存增强结果** —— 但那就退化成"固定副本"，等于没增强（坑 3）。

今天没做优化，因为剂量结论不依赖速度。但要记住：
**34 分 46 秒里有 25 分钟花在数据增强上。**

### 7.2 一个从 Day 18 潜伏到今天的 bug

sweep 跑完检查输出时发现的：第 1 组的 `train.log` 里有 **4 次**「输出目录」，
而后面 4 组的目录里**根本没有 `train.log`**。

根因在 `get_logger()`：

```python
logger = logging.getLogger(name)      # name 固定是 "train"
if logger.handlers:                   # 配过就直接返回
    return logger
```

`logging.getLogger("train")` 对同一个 name 返回**同一个对象**。
所以第二个 Trainer 调用时，`handlers` 非空 → 直接返回**第一个** logger
→ 它的 `FileHandler` 还指着第一组的目录。

**为什么潜伏了 5 天**：以前每个实验都是一条独立命令、一个独立进程，
一个进程里只 new 一个 Trainer。Day 23 的 sweep 在**同一个进程里连续 new 了 5 个**，
这才第一次踩到。

**为什么数据没受影响**：`history.json` 和 `curve.png` 走的是 `self.out`，
不经过 logger。只有 `train.log` 串了。这也是为什么"日志错了但数字是对的"
这种组合最容易骗人 —— 你去看日志会以为实验没跑。

**怎么发现的**：数日志里出现了几次「输出目录」。应该是 1 次，实际 4 次。
这个检查土得掉渣，但它有效 —— **日志本身不会告诉你它写错了地方**。

修法：判据从"handlers 空不空"改成"现有 `FileHandler` 指向哪个文件"。
同一个文件 → 复用；不同文件 → 换 handler。已单独提交（`68ebfb6`），
并用一个两次运行的探针验过。

### 8.3 我自己犯的错（今天五个）

1. **`argmax(dim=1)[1]` 取亮点位置** —— 平移把亮块移出那一行后，
   整行全 0，argmax 返回 0，六张图全报"列号 0"，看着像位移没生效。
   正确做法是 `sum(dim=0).argmax()`，把整图亮度投到 x 轴。
2. **`__main__` 与 `src.data.augment` 是两个类对象** ——
   `python src/data/augment.py` 时本模块叫 `__main__`，
   而 mnist.py 里 `from src.data.augment import ...` 会把同一文件**再加载一遍**。
   于是 `isinstance` 判 False，报错信息说"增强没生效"，
   但增强好得很，是断言用错了类。
3. **断言阈值定成"严格等于 0"** —— grid_sample 做不到，硬要求就是自找麻烦。
   容差应该卡在「只可能是舍入」的量级，而不是「必须是零」。
4. **关 7 的预判方向错了**（以为标准差会升，实际降了 6.1%）。
5. **`glob` 返回 Windows 反斜杠路径**，`split('/')[-2]` 直接 IndexError，
   而且 stdout 在缓冲区里没 flush，看起来像"一个文件都没找到"。
   用 `Path(p).parent.name`。

前两个是逻辑错，第三个是**验收标准**错，第四个是**直觉**错，
第五个是**平台差异**。五种都要靠"写断言 + 看实测"抓，光读代码一个都抓不到。
