# Day 26 · 混合精度：先证明值不值，再证明对不对

> 今天有两件事，顺序不能换：
>
> 1. **这台机器上 amp 值不值**（1660 Ti 是 sm_75 的 TU116，没有 Tensor Core）
> 2. **实现对不对**（手写 GradScaler + 六关）
>
> 为什么顺序不能换：如果先花一天把六关写完，最后才发现**它比 fp32 慢 1.5 倍**，
> 那这一天就白花了。**先测值不值，是省下一天的唯一办法。**

---

## 一、为什么值得单独一天

混合精度（amp）几乎是所有框架的"标配建议"，但它有三个容易被忽略的事实：

| 流行说法 | 实际成立条件 |
|---|---|
| "amp 能快 2 倍" | 需要 **Tensor Core**（RTX 20 系以上 / T4 / A100） |
| "amp 不影响精度" | fp16 只有 10 bit 尾数，**会影响**（今天实测 ep1 val_loss 差 20%） |
| "amp 只要加两行" | 两行能跑，但 `unscale_` 和 `clip` 的顺序、loss 的 dtype 都会让它**静默失效** |

这台机器三条都不满足。所以今天的产出不是"学会用 amp"，
而是**学会判断一个优化技术在你的硬件上值不值**，以及
**知道它会在哪里静默出错**。

---

## 二、fp16 的两个方向，方向不同、性质也不同

fp32 的指数位 8 bit（范围约 `1e-38 ~ 3e38`），fp16 只给 5 bit（`6e-8 ~ 65504`）。
尾数从 23 bit 掉到 10 bit。

```
上溢    数值 > 65504  → inf
下溢    数值 < 6e-8   → 变成 0
```

### 2.1 实测：下溢才是杀手

`python src/utils/amp_scaler.py --train` 关 2：

| 梯度值 | fp16 原样 | 变 0 | 放大 65536 后还原 | 变 0 |
|---|---|---|---|---|
| 1e-02 | 1.000e-02 | | 9.999e-03 | |
| 1e-03 | 1.000e-03 | | 1.000e-03 | |
| 1e-04 | 1.000e-04 | | 1.000e-04 | |
| 1e-05 | 1.001e-05 | | 1.000e-05 | |
| 1e-06 | 1.013e-06 | | 1.001e-06 | |
| 1e-07 | 1.192e-07 | | 1.000e-07 | |
| 1e-08 | **0.000e+00** | 是 | 1.000e-08 | |
| 1e-09 | **0.000e+00** | 是 | 1.000e-09 | |

**原样放 fp16：8 个里 2 个直接变 0。放大再还原：0 个变 0。**

注意 1e-05 / 1e-06 那两行放大后仍有 1~2% 的相对误差 ——
那是 **10 bit 尾数的精度损失**，不是下溢，两者要分开看。
**GradScaler 能解决下溢，解决不了精度。**

> fp16 最小正规格数 `6.10e-05`，靠 subnormal 能摸到 `5.96e-08`。
> fp32 能到 `1e-38`。
> **所以 1e-9 的梯度在 fp32 里完全正常，在 fp16 里是 0。**
>
> 而深度学习的梯度就常在这个区间。这就是为什么必须有 GradScaler，
> 也是为什么"fp16 不影响精度"这句话不成立。

### 2.2 上溢的门槛是 11.09，不是 65504

`exp(11.0899) = 65504` —— fp16 的 exp 在参数 11.09 处就到顶。关 4 实测：

| x | exp(x) fp32 | exp(x) fp16 |
|---|---|---|
| 10.00 | 2.203e+04 | 2.203e+04 |
| 11.00 | 5.987e+04 | 5.987e+04 |
| 11.05 | 6.294e+04 | 6.275e+04 |
| **11.09** | 6.551e+04 | **inf** |
| 12.00 | 1.628e+05 | inf |

但这里要**修正一个常见的说法**。P0 的笔记里写的是
"fp16 下 exp 溢出阈值 11.1，所以 CE 的 log-sum-exp 必须用 fp32"。
前半句对，后半句**不准确**，实测要分两种写法：

```
① 先减最大值再 exp（稳定版 log-sum-exp）
   exp 的参数 ≤ 0，结果永远 ≤ 1 → **fp16 也绝不溢出**
   Day 16 手写的 log_softmax 用的就是这一版
② 直接 exp(s)
   logits 一旦 > 11.09 就是 inf
```

所以真正会咬人的不是 ②，而是另一个更隐蔽的入口，见下面 2.3。

### 2.3 真正咬人的地方：loss 是 fp16 时，scale 一乘就爆

scale 的**初始值 65536 比 fp16 的上限 65504 还大**。所以：

```
loss(fp32) = 2.3  × 65536 = 150732.8   有限
loss(fp16) = 2.3  × 65536 = inf        ← 一乘就爆
```

`loss` 只要有 1.0，乘上初始 scale 就溢出。关 4 实测确认。

**那什么时候 loss 会是 fp16？** 这就是关 5 要回答的问题 ——
而我第一版把这一关写错了，值得单独记下来（见第七节错误 1）。

## 三、GradScaler 只做四件事

```
scale(loss)      loss *= scale            （前向之后、反向之前）
unscale_(opt)    grad /= scale，同时查 inf/nan
step(opt)        只有在没发现 inf/nan 时才真的更新
update()         按这一步的结果调大/调小 scale
```

手写版在 `src/utils/amp_scaler.py` 的 `MyGradScaler`，和官方逐步对拍。

### 3.1 为什么"发现 inf 就整步跳过"

一步的梯度里只要有一个参数是 inf，SGD 那一步就会把这个参数变成 **nan**，
而 nan 会顺着后续所有计算扩散到**全部参数**。
跳一步的代价是慢一步，可以忽略。

### 3.2 为什么砍半快、翻倍慢

```
炸一次    → scale *= 0.5，growth_tracker 清零
连续 2000 步没炸 → scale *= 2.0
```

**不对称是故意的**：一次 inf 说明"当前 scale 已经过大"，要立刻退回去；
而 scale 偏小时只是浪费一点精度，不致命。
所以"保守地大"比"激进地大"安全 ——
这和 Day 15 的早停 patience、Day 23 的增强剂量是同一种取向：
**在不确定的方向上选保守的那一侧。**

### 3.3 实测：scale 会自己找到量级

关 3 从**故意过大**的 `2^24 = 16777216` 起步：

| 步 | scale | 跳过 |
|---|---|---|
| 0 | 8.38861e+06 | True |
| 1 | 4.1943e+06 | True |
| 2 | 2.09715e+06 | True |
| 3 | 1.04858e+06 | True |
| 5 | 262144 | True |
| 12 | 262144 | False |
| 29 | 262144 | True |

**这就是动态 scaling 的全部智慧：不用猜该乘多少，从偏大的地方起步，
让 inf 检测自己把它压到合适位置。**

注意它在 262144 附近**来回跳**（有的步炸、有的步不炸）——
这不是 bug，是在边界附近震荡：涨两次就炸，炸了就砍半，再涨两次。
"稳定"指的是**数量级稳定**，不是"不动"。

### 关 1 · 逐步对拍 scale 轨迹

喂一段**人为设计**的 inf 模式（第 3、7、8 步注入 `inf`），
要求手写版和官方的 scale 序列、`growth_tracker`、以及"是否真的更新了参数"全部一致：

| 步 | 手写 scale | 官方 scale | 手写更新 | 官方更新 |
|---|---|---|---|---|
| 0 | 65536 | 65536 | True | True |
| 1 | 65536 | 65536 | True | True |
| 2 | 131072 | 131072 | True | True |
| 3 | 65536 | 65536 | **False** | **False** |
| 4 | 65536 | 65536 | True | True |
| 6 | 131072 | 131072 | True | True |
| 7 | 65536 | 65536 | **False** | **False** |
| 8 | 32768 | 32768 | **False** | **False** |

注意第 8 步：连续两次炸，scale 从 131072 砍到 65536 再砍到 32768。

**为什么这一关比"都对"更有说服力**：它同时验证了
"跳过的时机"（第 3、7、8 步）和"增长的节奏"（第 2、6 步）。
只比最终 scale 的话，跳过逻辑写错也能"对上"。

### 关 6 · 顺序错了不报错，步长差 65496 倍

这是今天最实用的一关。

| 顺序 | clip 前看到的 norm | 实际步长 \|Δw\| |
|---|---|---|
| ❌ clip 然后 unscale | **4.904e+05** | 1.527e-06 |
| ✅ unscale 然后 clip | 7.483 | **1.000e-01** |

**比值 65496 倍**（正好是 scale 的量级）。

写反的时候：clip 看到的是放大 65536 倍的梯度 → 全部被缩到 `max_norm=1.0`
→ 等于对真实梯度额外衰减了 65536 倍 → 步长只剩 `1.5e-06`。

**两次都没有报错，loss 也都在降**，只是写反那版慢了几个数量级。
所以这个坑必须靠**结构**堵死，不能靠记性 ——
这就是 `AmpStepper` 存在的理由。

## 五、AmpStepper：把顺序钉死在代码结构里

```python
class AmpStepper:
    def autocast(self):     # enabled=False 时返回 nullcontext()
    def backward(self, loss):    # loss 先升 fp32，再 scale
    def step(self, opt, params): # unscale → clip → step → update
```

训练循环里只有三行：

```python
with stepper.autocast():
    logits = model(xb)
    loss = crit(logits, yb)
stepper.backward(loss)
stepper.step(opt, model.parameters())
```

**为什么把 clip 也装进来**：如果 clip 留在外面，
`unscale_` 和 `clip_grad_norm_` 的相对顺序就变成了调用方的责任，
而写反不报错 —— 关 6 已证明它差 65496 倍，但 loss 曲线上只表现为"降得慢一点"。

这和 Day 25 用 `nn.Identity()` 替掉 `if has_bn:` 是同一个思路：
**让"写错"需要主动破坏封装，而不是忘记某一行。**

### 5.1 `loops.py` 不认识 Config，这条原则被检验了一次

需要让训练循环知道"要不要 autocast、要不要 scaler"，有两条路：

| 做法 | 后果 |
|---|---|
| ❌ 传 `cfg` 进来，循环里 `if cfg.amp == "fp16":` | 循环从此认识配置系统，以后每个 amp 字段都要在这里加分支 |
| ✅ 传一个已经装好的 `AmpStepper`，循环只调它的三个方法 | 循环仍然不认识 Config，只认识"一步怎么走"的小对象 |

选了后者。代价是 `loops.py` 多一个可选参数（默认 `None` = 纯 fp32），
收益是 amp 的全部复杂度被关在 `src/utils/amp_scaler.py` 一个文件里。

### 5.2 评估永远走 fp32

`trainer.py` 里 `evaluate()` **不套 autocast**，即使是 amp 训练。这不是漏了：

> 训练用 fp16 算出的权重，要用**同一把尺子**去量。
> 如果训练 fp16、评估也 fp16，那"fp16 的 0.9917"和"fp32 的 0.9936"
> 就是两种仪器测出来的数，没法直接比 ——
> 而今天要回答的恰恰是"amp 影响不影响结果"。

评估只占一轮的 10% 左右，省这点时间不值。

## 六、实测：这台机器上 amp 值不值

### 6.1 单个训练步（`scripts/bench_amp.py`）

| batch | fp32 | amp | amp/fp32 | fp32 显存 | amp 显存 | 省显存 |
|---|---|---|---|---|---|---|
| 64 | 2.4ms | 3.8ms | 1.56x | 37MB | 28MB | 25% |
| 128 | 3.2ms | 5.0ms | 1.58x | 55MB | 36MB | 34% |
| 256 | 4.0ms | 7.2ms | 1.79x | 97MB | 53MB | 46% |
| 512 | 7.2ms | 29.6ms | **4.09x** | 172MB | 87MB | 49% |
| 1024 | 14.0ms | 58.1ms | **4.15x** | 327MB | 156MB | 52% |

**没有一个 batch size 上 amp 更快。** 而且 batch 越大差距越大。

- 不是"某个配置下不划算"，是**这个 GPU + 这个模型根本不划算**
- 原因：sm_75 的消费卡（TU116）没有 Tensor Core，fp16 的 GEMM 不走加速路径，
  只剩类型转换的额外开销；batch 大了之后转换的量也变大，所以差距拉大
- **省显存是真的（25%~52%），提速是假的**

### 6.2 端到端一轮（含数据加载）

| 配置 | ep1 | ep2 | ep3 | test acc | 总时间 |
|---|---|---|---|---|---|
| fp32 | 0.0590 | 0.0416 | 0.0467 | 0.9873 | **41.7s** |
| fp16 + scaler | 0.0710 | 0.0463 | 0.0406 | 0.9891 | 45.2s |

- 端到端 amp **慢 8.4%**（45.2 vs 41.7）。比单步的 1.58x 温和得多，
  因为一轮里还有约 12 秒花在数据加载上 —— **它把 amp 的劣势稀释了**
- fp16 组 1266 步里**跳过 1 步（0.08%）**，最终 scale 32768
- `test acc` 0.9891 vs 0.9873，差 0.18pt —— 记住 Day 25 立的基准线
  **实现噪声就有 2.0 SE**，这个差值在噪声里，不能说 fp16 更好或更差

⚠️ **ep1 的 val_loss 差 20%（0.0710 vs 0.0590）**，这是 fp16 精度损失的直接读数。
到 ep3 收敛后差距消失。这条值得记住：**amp 影响的是"前几轮怎么走"，
不一定影响"最后到哪"** —— 和 Day 25 BN 的结论形状一样（收敛过程变了，上限没变）。

### 6.3 所以默认值

`configs/cnn_amp.yaml` 里 `amp: fp16` 存在，但 **`Config.amp` 的默认是 `none`**。

> **默认值应该跟着实测走，不该跟着流行说法走。**
> 这台机器上 amp 更慢、更耗精度，只有一个真实收益（省显存）。
> 等到模型大到 fp32 装不下，或者换到有 Tensor Core 的卡，再改这个默认值。

这和 Day 27 里 `data_backend` 默认设成 `u8` 是同一条原则的两个方向：
**u8 因为没有取舍所以设成默认；amp 因为有取舍所以不设。**

## 七、我自己犯的错（今天三个）

### 1. 把"手写 loss 一定返回 fp16"当成了事实

关 5 的第一版我直接假设 `HandCE` 在 autocast 下返回 fp16，然后写断言。
实测返回的是 **fp32** —— 因为 Day 16 那版用的
`max / sub / exp / sum / log / gather / mean` **全部在 autocast 的 fp32 promote 列表里**。

真正危险的是**loss 里出现 matmul / mm / bmm / conv / linear**：

| 写法 | dtype | ×65536 |
|---|---|---|
| 只含归约算子（Day 16） | float32 | 有限 ✅ |
| 末尾套一次 1×1 matmul | **float16** | **inf** ❌ |
| 官方 CrossEntropyLoss | float32 | 有限 ✅ |

**教训**：结论要精确到"触发条件"这一层，不能停在"手写就危险"。
"手写"不是危险的原因，**"用了 autocast 不 promote 的算子"** 才是。

而且这一条修正了两处旧笔记：
- P0 说"CE 的 log-sum-exp 必须用 fp32"→ 稳定版写法 fp16 也不会溢出
- 我原以为"手写 loss 没有 autocast 的待遇"→ 取决于写法

### 2. 关 2 的断言把"精度损失"当成了"下溢"

第一版断言写的是 `lost_raw > lost_scaled`，而 `lost_scaled` 的判据是
`(x*65536)/65536 != x` —— 这会把 1e-5 那种 1% 的精度误差也算成"丢失"，
于是出现"8/8 个值找不回来"的荒谬结论。

正确判据是**只数变成 0 的个数**：原样 2/8，放大后 0/8。
**下溢和精度是两件事，不能用同一个判据。**

### 3. 在 `if __name__` 块里定义类

Windows 上 `num_workers>0` 用 spawn，子进程要按名字 import 类。
写在 `main()` 里就报 `Can't get attribute 'TensorMNIST'`。
类必须定义在**模块顶层**。这条是 Day 27 踩的，但根源在 Day 26 的探针脚本里。

### 8.2 三条跨天结论

1. **一个优化技术的价值是"硬件 × 模型"的函数，不是常数。**
   同一份代码，在有 Tensor Core 的卡上是 2x，在这台机器上是 0.63x。
   凡是"某技术能快 N 倍"的说法，都要问"在什么硬件、什么模型上"。
2. **先测值不值，再证明对不对。** 顺序反了就白干一天。
   六关全部通过只证明实现是对的，**不证明它有用**。
3. **凡是"顺序不能换"的多步流程，都应该封装成一个原子操作。**
   `unscale→clip→step→update` 里任何一步换位置都不报错，
   而错 65496 倍。这种地方不能用注释提醒，要用结构。

### 8.3 回归检查

`amp=none` + `grad_clip=0` 跑 2 轮，与 Day 25 的 `bn1_none` 逐字段对比：
**16 个值，0 个不同。**

→ Day 26 的整套改动没有碰到 fp32 路径的任何一位。

### 8.4 留给后面的账

- **amp 的显存收益还没有实际用上**：今天只证明了"省 52%"，但没跑一个
  "fp32 装不下、fp16 装得下"的实验。这件事要等模型大起来才有意义。
- **`grad_clip` 的剂量没扫**：今天只用了 `1.0` 这一个值演示顺序问题，
  没有回答"这个任务该裁多少"。记进 P2（PPO 会强制用它）。
- Day 27：数据加载。今天的实测已经暴露了意外线索 ——
  端到端 amp 只慢 8.4%，因为数据加载占了 12 秒。**那 12 秒才是大头。**
