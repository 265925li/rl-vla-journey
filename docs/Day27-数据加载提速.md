## 一、Day 24 留下的前提，第一步就被打翻了

Day 24 的结论是这样写的：

> 每轮 13.55s，其中 CNN 前反向 9.48s，剩下 **4.07s（30%）** 是数据加载与拷贝。

于是 Day 27 的既定任务是"把那 30% 优化掉"，起手先算 Amdahl：
把 4.07s 优化到 0，最多 `13.55 / 9.48 = 1.43x`。

**然后我量了一遍。** `scripts/bench_data.py --only 1`：

| 环节 | 耗时（54000 张，422 批） |
|---|---|
| `Dataset.__getitem__` | **8.29s** |
| `default_collate` × 422 | 0.08s |
| `collate` + 增强 × 422 | 0.45s（增强净 **0.88ms/批**） |
| H2D 拷贝 × 422 | 0.27s |

三个结论，每一个都和预期不同：

1. **数据侧不是 4.07s，是 9s 左右** —— Day 24 那个 4.07s 的拆法错了
2. **增强只占 0.45s** —— 那是 Day 24 花一整天优化的对象
3. **`__getitem__` 占 8.29s** —— 这一项从来没被单独看过

### 1.1 8.29 秒花在哪

torchvision 的 MNIST 在 `__getitem__` 里做的是：

```python
img = Image.fromarray(self.data[index].numpy())   # 造一个 PIL 对象
return self.transform(img)                        # ToTensor：再转回张量
```

所以数据**本来就在内存里**（一个 `(60000,28,28)` 的 uint8 张量），
却要绕过 PIL 转一圈再转回来。单张 142.7µs，而真正的数值计算（`float(x)/255`）
不到 5µs。

> **这就是"先量再改"的价值：不量的话，你会去优化一个占 3% 的东西，
> 而看着那个占 90% 的东西说"这个没法优化"。**
>
> 顺带一个方法论提醒：Day 24 那个"剩下 4.07s"是怎么来的？
> 大概率是拿"总时间 − 实测的前反向时间"倒推的。**倒推的拆解不是测量。**
> 差值的来源可以是数据加载，也可以是别的没被想到的东西 ——
> 只有真的把每一项单独计时，才知道差值是什么。

## 二、改法是"换后端"，不是"加并发"

三个后端，每一级都更快：

| 后端 | 做法 | 单条读取 | 一轮（含增强） | 相对 pil | 额外内存 |
|---|---|---|---|---|---|
| `pil` | torchvision 原样（PIL 往返） | 142.7µs | 7.72s | 1.00x | 0 |
| `u8` | 直接索引 uint8 张量，逐样本转 | 47.2µs | 2.82s | **2.74x** | 0 |
| `f32` | 启动时一次性转 float32 常驻 | 13.0µs | 1.11s | **6.93x** | +179MB |

### 2.1 为什么这是"纯提速"，没有精度权衡

`ToTensor()` 对 uint8 灰度图做的事就是：

```
float(uint8) / 255
```

这是**逐元素的同一个除法**，没有插值、没有近似。
所以"换后端等价"是可证的，不只是"应该差不多"。三道关把它钉死：

| 关 | 内容 | 实测 |
|---|---|---|
| 关 1 | u8 vs PIL，8 个下标逐位 | `0.00e+00` |
| 关 2 | f32 vs PIL，4 个下标逐位 | `0.00e+00` |
| 关 3 | 端到端 422 批 × 增强 × shuffle | x 差 `0.00e+00`，标签 422/422 全同 |

**关 3 是最硬的一关**：单条对拍过了不代表端到端对拍过 ——
中间还有 shuffle 的随机流（独立于增强的另一条）、collate 的 stack 顺序。
两条随机流只要有一条没对齐，结果就完全不同。

### 2.2 端到端：真实训练的 2 轮

| 后端 | ep1 | ep2 | 2 轮总计 |
|---|---|---|---|
| `pil` | 12.12s | 13.63s | 25.8s |
| `u8` | 5.57s | 5.84s | **11.4s（2.26x）** |
| `f32` | 3.64s | 3.30s | **6.9s（3.74x）** |

**3.74 倍，而 18 个数值（2 轮 × 7 字段 + test 4 个）0 个不同。**

比 Amdahl 预估的 1.43x 大得多。为什么：
数据加载在 **CPU** 上串行进行，模型在 **GPU** 上 —— 两者本来是串行的。
把 CPU 侧的 8 秒压到 1 秒，整轮就从 13 秒掉到 3.6 秒。

> **Amdahl 的前提是"各部分串行相加"。这里的实际结构是
> "CPU 等待 → GPU 计算 → CPU 等待"，所以砍掉 CPU 时间直接砍掉整轮时间。**
> 定律没错，是我对"占比"的理解错了 —— 又一次"倒推的拆解不是测量"。

### 2.3 `u8` 和 `f32` 怎么选

`Config.data_backend` 的默认是 **`u8`**，理由：

- 与 `pil` **逐位相同**（差 `0.00e+00`）
- 额外内存 **0**（MNIST 本来就以 uint8 在内存里，等于没多占）
- 快 **2.26x**（端到端）

**没有任何取舍的改动，就不该留成"可选优化"。**

`f32` 是**有取舍**的（+179MB 换 1.6x），所以不设成默认。
什么时候值得开：数据集小到能整个装进内存、而且要跑几十轮的时候。
一次性的 179MB 换每轮省 2.3 秒，25 轮就是 57 秒。

> ⚠️ 179MB 是**整个 60000 张**，不是切出来的 54000 张 ——
> `Subset` 只是下标视图，底层张量是共享的，验证集也要用。
>
> 这条和 Day 25 的 `state_dict()` 是同一类知识：**你得知道那个数组到底被谁共享着。**

### 2.4 新增的 `data_backend` 字段

```yaml
data_backend: pil   # pil / u8 / f32
```

默认 `u8`，`--set data_backend=pil` 就回到 Day 26 的行为。
那一条通用通道（Day 18 的 `--set`）第四次兑现：**加字段不用改 cli**。

## 三、num_workers：三个独立的问题

既定任务是"用 `num_workers>0` 吃掉剩余耗时"。实测下来这条路走不通，
而且**不是"调不好"，是三个各自独立的原因**。

### 3.1 问题一：挂增强的 collate 根本不可 pickle

第一步就崩了：

```
AttributeError: Can't pickle local object
'make_augment_collate.<locals>.collate'
```

原因：Day 24 把增强挪进 `collate_fn` 时，返回的是**闭包**：

```python
def make_augment_collate(...):
    def collate(batch):        # ← 局部函数，pickle 无法重建
        ...
    return collate
```

而 Windows 上 DataLoader 用 **spawn**，collate 要靠 pickle 送进子进程。

> **这个 bug 从 Day 24 就存在，三天里一直没暴露，
> 因为一直用 `num_workers=0`。**
>
> **不是"新引入的 bug"，是"原来那条路根本没被走过"。**
> 这类问题最值得记：你的测试覆盖不到的分支，会安静地烂很久。

修法：改成类 `AugmentCollate`（`torch.Generator` 恰好可 pickle）。
关 5 断言的是**"能被 pickle 且往返后行为不变"**（往返后输出差 `0.00e+00`），
不是"是不是类" —— 断言行为比断言实现活得久，这是 Day 23 的教训。

### 3.2 问题二：generator 被原样复制，增强参数重复

改完 3.1，`num_workers=2` 能跑了。但结果和 `num_workers=0` **不一样**：

| 配置 | 与 num_workers=0 逐位相同的批 |
|---|---|
| `num_workers=2` | 1/8 |

关 6 用一个"所有图都长一样"的数据集把这个机制钉死：

```
per_worker_gen=False 时 batch0 与 batch1 相同：True
```

输入全同的两个批，输出也全同 —— 说明它们抽到了**同一组**增强参数。

为什么：`num_workers=W` 时 collate 对象被 pickle 到 W 个子进程，
**每份都是完全一样的副本，包括 generator 的当前状态**。
于是 worker 0 的第 1 组随机数 == worker 1 的第 1 组 == ……
而 batch i 由 worker (i mod W) 处理，所以 **batch 0..W-1 用的是同一组参数**。

W=4 时效果是"每 4 个批里有 1 组参数被重复用 4 次"，
**增强剂量被打了折，而 loss 曲线完全正常，看不出来。**

两种应对，**不可兼得**：

| 设置 | 保住逐位可比 | 保住增强多样性 |
|---|---|---|
| `per_worker_gen=False`（默认） | ✅ | ❌ |
| `per_worker_gen=True` | ❌ | ✅ |

`per_worker_gen=True` 的做法是在**子进程里懒创建** generator，
seed 用 `seed * 1_000_003 + worker_id` 派生
（必须懒创建 —— `__init__` 跑在父进程，那时还不知道 `worker_id`）。

### 3.3 问题三：spawn 的成本比省下的时间大得多

即使两个问题都解决了，性能上还是亏的。关 6 之外单独测了 spawn 成本：

| 后端 | workers | 起进程 | 消费 422 批 | 合计 |
|---|---|---|---|---|
| u8 | 0 | 0.00s | 3.05s | **3.05s** |
| u8 | 1 | 5.15s | 3.78s | 8.93s |
| u8 | 2 | 10.18s | 2.37s | 12.55s |
| u8 | 4 | 20.55s | 1.90s | 22.46s |
| f32 | 0 | 0.00s | 1.26s | **1.26s** |
| f32 | 4 | 20.63s | 1.45s | 22.08s |

**每个 worker 的启动成本约 5.1 秒**，而且消费时间只从 3.05s 降到 1.90s（4 worker，1.6x）。

> 并行**确实有效**（3.05 → 1.90），但"启动一次"的成本远大于"干完这次的活"。
> Windows 没有 fork，每个子进程都要重新 `import torch` + 反序列化整个 dataset。

用 `persistent_workers=True` 把 spawn 摊到多个 epoch 也没救回来：

| 后端 | workers | persistent | 3 epoch | 每 epoch |
|---|---|---|---|---|
| u8 | 0 | — | 9.28s | **3.09s** |
| u8 | 2 | False | 38.11s | 12.70s |
| u8 | 2 | True | 15.61s | 5.20s |
| u8 | 4 | True | 23.85s | 7.95s |
| f32 | 0 | — | 3.81s | **1.27s** |
| f32 | 2 | True | 13.43s | 4.48s |

**persistent 从 8 倍慢降到 3.5 倍慢，仍然亏。**

真实训练也验证了这一点（2 轮）：

| 配置 | ep1 | ep2 | 总计 |
|---|---|---|---|
| `u8`, nw=0 | 5.57s | 5.84s | 11.4s |
| `u8`, nw=2 | 27.32s | 27.05s | **54.4s** |
| `f32`, nw=0 | 3.64s | 3.30s | **6.9s** |
| `f32`, nw=2 | 27.38s | 26.90s | **54.3s** |

**慢 8 倍。** 而且 `num_workers=2` 那两行的数值也不对
（ep1 `train_loss` 0.4324 vs 0.4475）—— 3.2 那个问题的直接后果。

### 3.4 判据：什么时候 num_workers 才值得

可以直接拿去用的式子：

```
num_workers 值不值得
    = 每 epoch 能省下的时间 > spawn 成本 / 计划跑多少轮
```

这个任务代进去：能省 `3.05 − 1.90 = 1.15s/epoch`，
4 worker 的 spawn 要 `20.6s` → **要么轮数 > 18，要么单个 epoch 的数据量大 18 倍以上。**

而这个任务**跑满 25 轮，每轮 422 批**，两条都不满足。

> 所以 Day 27 的验收标准（"`num_workers=0` 与 4 逐位一致"）
> 不只是"做不到"，而是**这个方向本身不该走**。

## 四、那"逐位一致"到底能不能做到

能，但要改随机流的组织方式，而且要同时改三处。

**现在的做法**：一条顺序流，按批依次消耗。

```
batch0 抽 r[0..383]   batch1 抽 r[384..767]   ...
```

切成 W 个 worker 之后，这条流被分成 W 条，**拼不回原来的顺序**。

**能保住逐位的做法**：把"随机数"从"顺序消耗"改成"按位置索引"。

```
预先在父进程算好一整轮的参数表
    params[0..53999] = 抽 3×54000 个数（顺序与现在完全相同）

每个样本按它在这一轮里的**位置**去查表
    位置 → 由 sampler 决定，与 worker 调度无关
```

这样：

- `num_workers=0` 和 `=4` 查的是同一张表 → **逐位相同**
- 随机流与现在完全一致 → **历史结果可比**
- 但需要 **sampler 产出 (idx, pos)**、**dataset 把 pos 传下去**、
  **collate 用 pos 查表** —— 三处一起改

代价是复杂度，收益是"并行 + 可复现"兼得。
**这个任务上不值得做**（省 1.15s/epoch），但换成 ImageNet 那种
"读取要几分钟、要跑 100 轮"的场景，它就值得了。

> 这一节是今天最该带走的方法论：
> **"可并行"和"可复现"的冲突不在并行本身，在"随机数怎么被抽"。**
> Day 24 已经踩过同一个坑（逐样本 → 整批时随机序列被换掉），
> 那次是靠"一次抽 3n 再 reshape"解决的。今天这个更难，
> 因为切的不是"什么时机抽"，是"由谁抽"。

## 五、今天犯的错

### 1. 信了 Day 24 的"4.07s"没有复测

整整一天的方向都建立在那个数字上。真正量一遍之后，
瓶颈位置完全相反（数据侧 9s / 模型侧 1.5s，不是 4s / 9.5s）。

**教训**：**上一个结论里的数字，如果它是"推出来的"而不是"测出来的"，
用它之前要复测。** 讲义里凡是估算必须标"估算"，就是为了防这个。

### 2. 在 `if __name__` 块里定义类

`TensorMNIST` 定义在 `main()` 里，spawn 的子进程按名字 import 时找不到：

```
AttributeError: Can't get attribute 'TensorMNIST' on module '__mp_main__'
```

类必须定义在**模块顶层**。这是 Windows + spawn 的硬约束。

### 3. 改 collate 时忘了它会"变成两条路径"

`per_worker_gen` 这个开关加到 `build_train_loader` 之后，
同名的 `num_workers` 参数就有了**两种含义**（"用几个进程" 和 "要不要牺牲可对拍性"）。
第一版我把 `per_worker_gen` 直接塞进 `kwargs` 里，
结果它被当成 DataLoader 的关键字参数，报 `unexpected keyword argument`。

**教训**：给一个已经有很多参数的函数加"模式开关"要小心 ——
**两个正交的维度不要挤进同一个参数名。**

### 6.2 四条跨天结论

1. **"剩下的时间"必须真的量，不能倒推。**
   倒推出来的差值可以是任何东西。Day 24 的 4.07s 和实测的 9s 差了 5 秒，
   而那 5 秒恰好是唯一值得优化的部分。
2. **优化完瓶颈之后，原来的第二瓶颈会变成新瓶颈，而它的方案未必还成立。**
   数据侧压到 1.1s 之后，`num_workers` 从"值得考虑"变成"绝对不要"。
   **Amdahl 定律要用两次**：优化前算一次上限，优化后重新算一次。
3. **"可并行"和"可复现"的冲突在"随机数由谁抽"，不在并行本身。**
   要兼得就得把随机流改成"按位置索引"，代价是 sampler/dataset/collate 三处一起改。
4. **没被走到的分支会安静地烂很久。**
   `num_workers>0` 这条路从 Day 23 就断了（闭包不可 pickle），
   三天没被发现，因为一直 `num_workers=0`。
   **加一个"开关型"参数时，至少要有一次把它打开的测试。**

### 6.4 留给后面的账

- **`f32` 后端的 179MB 在多进程下会翻倍**：每个 worker 都要反序列化一份。
  今天没用多进程所以没暴露，换场景要注意。
- **`pin_memory=True` 没测**：加了这个参数但没验证收益。
  H2D 拷贝实测只有 0.27s，理论上限很低，但没量过就不该写进结论。
- **大数据集下 `num_workers` 的结论可能反过来**：今天给的是判据
  （"省下的时间 > spawn / 轮数"），不是"永远别用"。换数据集要重算。
